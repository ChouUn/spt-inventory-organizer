# 按网格计分实现的耗时分布与预算实验

> Parent: [../index.md](../index.md)
> Status: 本地测量完成（2026-09-11），尚未测量本版本游戏内事务耗时
> Scope: 每个网格内部加权、最后累加的当前实现
> Related: [全局排布计划](../plans/global-packing.md)

## 结论

这份仓库快照的最终输出在初始布局生成时已经得到。
3 秒预算下，约 2.84 秒花在一次 CP-SAT 调用里；没有找到优于初始布局的结果。
七档预算的 42 次回放输出逐字节相同。
取消最终 CP-SAT 搜索、保留初始布局生成时，首次整理中位数为 233 毫秒。
这些结果回答当前快照是否可以缩短等待，不构成所有库存都无需搜索的结论。

## 测量方法

输入固定为 `.temp/stash-snapshots/20260910-211258-fixed-tag/replay.json`。
垃圾箱标签为 `@o !n:狗牌;`，使用快照原有物品、尺寸、类别、锁和堆叠数量。
本次只比较当前网格内计分实现的不同预算，不使用其他实现作为性能基线。

在 `.temp/budget-profile/Core/` 复制当前 Core，增加计时和实验预算入口。
折叠、堆叠、收纳、最终排布分别计时；最终排布继续分成初始布局、建模、
求解调用及身份映射。正式源码和部署文件未改动。
规则收纳保留当前面积目标及每次 1 秒、累计 2 秒上限；
实验仅改变最终排布可用的整次余量，计算为实验预算减去已用收纳预算。
当前输入的所有收纳请求均达到面积界限，直接返回，没有启动 CP-SAT。

七档预算各三个独立进程，交错执行；每个进程首次整理后立即重复整理一次。
共 42 次，均校验数量守恒、归属、固定物品、网格边界及无重叠。
所有输出快照与本实现 3 秒结果逐字节相同，包括真实 ID、坐标、转置与数量。
首次收纳均为 56 件，重复收纳为 0；没有待折叠或待合并项，无警告或失败。

另外单独启用一次详细求解日志，观察初始解及后续搜索。
详细日志的耗时不混入三次中位数。
再用与已部署 DLL 哈希相同的正式程序集复核 3、0.5、0 秒各一次：
通过回放端在最终排布前扣减实验实例的剩余预算，不修改程序集。
这六次输出同样完全一致；0 秒首次 225 毫秒，重复 31 毫秒。

## 3 秒用在哪里

以下为 3 秒档首次整理三次中位数；阶段之间不重叠。
总耗时约 3205 毫秒，预算约束规划额度，原生初始化、线程调度及应用还有额外开销。

| 阶段 | 耗时 | 工作 |
| --- | ---: | --- |
| 折叠 | 9.6 ms | 读取快照、遍历，没有折叠事务 |
| 统一堆叠 | 26.9 ms | 读取与建立索引，没有合并事务 |
| 按规则收纳 | 100.3 ms | 匹配、规划、更新状态及内存移动事务 |
| 最终排布 | 3068.6 ms | 生成布局、建模、搜索及应用 |

收纳阶段内，四个目标的规划合计约 56 毫秒。
四次快照读取合计约 22.5 毫秒，已包含在对应阶段里，不能重复相加。
最终排布的子项如下；未列出的少量开销包括调用初始化、缓存、校验及结果读取。

| 最终排布子项 | 耗时 |
| --- | ---: |
| 匿名身份准备 | 5.0 ms |
| 全部网格的初始布局生成 | 75.7 ms |
| 网格通用最优界限检查 | 1.8 ms |
| C# 模型构造，含此路径首次运行开销 | 100.3 ms |
| CP-SAT 调用 | 2843.4 ms |
| 真实 ID 映射 | 0.8 ms |

五个网格中仓库、武器箱、垃圾箱进入同一个求解调用；
弹药箱和狗牌包达到通用界限，保留初始布局。
四层类别合在一个 `grid-sum` 目标里。

详细日志显示，原生求解器约在 0.28 秒结束预处理，接收完整初始解后开始搜索。
本次原生调用持续 2.763 秒，其中约 2.48 秒为后续搜索，探索了 21681 个分支。
只记录到初始解，结束时的目标值与初始值相同，状态为 `Feasible`。
它既没有改善布局，也没有完成最优性证明。
CP-SAT 调用的外层计时还包含原生初始化、封送与返回开销，不能与原生日志直接相加。

## 缩短预算的结果

表中为各档三次中位数。
0 秒表示最终 CP-SAT 不搜索，收纳、初始布局生成、身份映射和校验照常执行。

| 实验预算 | 首次总耗时 | 立即重复耗时 | 与本实现 3 秒的完整输出 |
| --- | ---: | ---: | --- |
| 3 s | 3205 ms | 3047 ms | 相同 |
| 2 s | 2208 ms | 2049 ms | 相同 |
| 1 s | 1205 ms | 1046 ms | 相同 |
| 0.5 s | 694 ms | 553 ms | 相同 |
| 0.25 s | 447 ms | 295 ms | 相同 |
| 0.1 s | 235 ms | 191 ms | 相同 |
| 0 s | 233 ms | 35 ms | 相同 |

0.25、0.5 秒档的三次首次调用均返回 `Unknown`，没有产生可行求解响应；
0.5 秒单次详细日志明确记录在预处理后停止。
编排采用已经生成的合法初始布局，结果仍相同。
1～3 秒档虽返回 `Feasible`，接受的仍为初始解。

重复整理时，收纳更快，使最终可用预算略增；当前缓存要求旧预算不少于新预算，
因此仍会再次搜索。0 秒档的最终额度两次都是 0，重复整理可以命中缓存。
这个现象解释了 0.1 秒与 0 秒重复耗时的差异；本轮没有修改缓存策略。

## 适用范围与证据

对这份快照，可以保留相同输出并省去约 2.97 秒等待。
这一测量支持后续研究短预算或停止条件；本轮没有改变正式预算。
初始布局不保证对其他库存同样有效，当前 3 秒结果也没有证明全局最优。
本地出口为内存事务，不包含 Unity 视图重建、其他模组监听或网络等待。
游戏日志停留在旧部署的记录，本轮没有将其作为当前版本耗时使用。

全部实验工程、原始计时、搜索日志、完整快照与汇总在 `.temp/budget-profile/`。
`prepare.py` 生成临时计时副本，`run.py` 执行七档实验，
`prepare-exact.py` 生成正式程序集复核入口，`summarize.py` 校验并汇总结果。
两个测量工程构建零警告、零错误。
正式 Core 哈希见 `.temp/budget-profile/report.md`，与已部署版本一致。
