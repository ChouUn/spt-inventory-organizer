# 原生排序与 Stash Management Helper 离线对照

> Parent: [../index.md](../index.md)
> Status: 离线回放完成，修复后游戏对比日志核验通过（2026-09-11）
> Related: [../feats/packing.md](../feats/packing.md)

## 结论

StashManagementHelper 的排序和落位算法可以在游戏外运行。
同一散乱仓库经折叠、堆叠和规则收纳后，五个网格的最终排布计算：
本项目预热后中位数 **882 ms**，原生算法 **2.25 ms**，
Stash Management Helper（SMH）**2.92 ms**。
本项目与 SMH 都把仓库压到 61 行，本项目的父类聚合明显更紧。
这些数据比较排布算法，不代表完整 mod 在游戏里的按钮响应时间。

SMH 使用本机配置副本：Custom；容量降序、物品面积降序；
类型、重量和商人价格排序关闭；允许转置、不反向、不跳行。
SMH 的自定义落位只对 `hideout` 网格生效，子容器采用原生落位。
两个阶段都保留：先原生列表排序，再 SMH 自定义排序；随后逐件找位置。

## 测量边界

基准执行游戏 DLL 的 `ItemSorter.Sort`、网格空位搜索与占用缓冲更新，
SMH 执行安装版 DLL 的 `SortingStrategy.Sort` 与 `FindPlacement`。
落位驱动保留原生逐件放置和最多五次回退的流程，固定每个网格的物品集合。
占用更新只写新建的临时缓冲；没有调用真实物品增删、控制器或网络事务。
计时不含输入还原、校验、输出文件、游戏限制检查、事务回滚和 UI 刷新。
本项目计时为正式最终规划的完整耗时，含初始布局、建模、求解和身份映射。

离线适配包含两处运行环境处理，均只发生在 `.temp/` 的副本：

1. 游戏程序集有 CLR 无法加载的 Mono 委托类型，原生初始化的全程序集类型枚举
   改为由元数据提取完整的 126 个公开 Item 类型；类型排序算法不变。
2. JSON 库使用官方 Newtonsoft.Json 13.0.3，避免游戏修改版的强名称校验失败。

物品以实际游戏 C# 类型承载快照尺寸、实例与模板 ID、数量、容器容量和狗牌字段。
尺寸已经包括折叠与挂件影响；没有重建完整挂件及内部库存树。
重量排序关闭，简化的内部树不影响本次排序键，但会低估 SMH 预计算总重量的遍历成本。
因此这是原算法的离线回放，不是完整游戏对象与 Unity 运行时的等价性能测试。
Debug 游戏日志使用真实物品读取尺寸和原生排序键，可补充实际运行时的测量。

不调用 SMH 的 `SortPatch`：其合并、折叠前置逻辑即使接收到 `simulate=true`，
仍可能提交网络事务。测试也没有改动游戏中的 UIFixes 或 SMH 配置。

## 首次游戏日志与修复

2026-09-11 首次游戏验证中，四次正式整理均成功，原生对比均未执行：
`sort-benchmark unavailable: native dependency patched: FindFreeSpaceInGrid`。
上文的毫秒级原生与 SMH 数据仍只是离线测量，不能当作本次游戏实测。

UIFixes 的 `FindSpotKeepRotationPatch` 和 `FindPlaceToPutPatch` 分别修改
`FindFreeSpaceInGrid`、`GetFreeLocation`，启动日志确认这两个补丁均已启用。
原实现只复制最上层搜索，对已打补丁的下层方法直接报错退出，遗漏了该兼容场景。

修复将三层搜索方法一起复制，并把副本内部的调用重定向到原生副本。
正常游戏调用仍保留全部第三方补丁，真实库存与配置不变。
回归测试给三层方法同时加拒绝补丁，确认基准仍能正确搜索并转置，
普通调用仍受补丁影响；Plugin 测试 6/6 通过。
实际 Harmony 烟雾测试给下层方法加抛错补丁后也通过，游戏日志待再次验证。

| 散乱仓库 | 3008 ms | 1055 ms | 1724 ms | 72→61 行，318 件换位 |
| 已整理垃圾箱 | 584 ms | 580 ms | 无 | 保持 10 行，无换位 |
